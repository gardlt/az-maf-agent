## SR-01 — High: Free deletion requests exhaust the global run ledger

**Locations:** `apps/agent/src/az_maf_agent/guardrails.py:216–223`; `apps/agent/src/az_maf_agent/core.py:354–358` and `memory_async`.

**Prerequisite:** An admitted user with memory access on a deployment with shared guardrails, as configured for dev.

**Attack vector / reproduction:**

1. Create a session for user A and a separate session for user B.
2. As A, repeat `DELETE /sessions/{A-session}/memory` 1,000 times, sequentially. The preference store can already be empty.
3. As B, call `GET /sessions/{B-session}/memory` or begin a new chat run.
4. Observe `429 {"error":"control_capacity"}`. The same global admission cap applies to all new supervised runs.

**Observed evidence:** All 1,000 deletions succeeded. The shared state contained 1,000 completed runs and no daily model charges (`daily == {}`). B's inspection returned `control_capacity`.

**Root cause / impact:** Every memory operation creates a run, but deletion is deliberately exempt from the session memory counter. Sequential operations evade concurrency limits and never reserve model spending. Completed runs remain in the single shared ledger until `deadline + 86400`; once its 1,000-record cap is reached, all users lose new supervised operations for roughly 24 hours without operator intervention. This also blocks legitimate deletion requests. The same capacity can be reached by sufficient ordinary traffic.

**Concrete remediation:** Separate active/unresolved execution state from terminal history. Archive terminal runs outside the hot admission document; keep compact replay fences for the required replay window and preserve unresolved effects and daily reservations. Add atomic per-principal request-rate/admission limits for non-model operations. Make repeated empty-state deletion idempotent without allocating a fresh long-lived run, while preserving deletion fencing and necessary audit. Ensure privacy deletion retains bounded capacity under general admission pressure. Merely increasing the 1,000-record limit delays the attack.

**Regression requirement:** A's repeated no-op deletions must not prevent B's chat or deletion; terminal archival must not permit approval replay, refund budgets, or discard unresolved outcomes.

## SR-02 — High: Stage/prod profiles permit live service without shared safety controls

**Locations:** `infra/main.bicep:37`, `infra/main.bicep:124–141`; `infra/main.stage.bicepparam`; `infra/main.prod.bicepparam`; `apps/agent/src/az_maf_agent/api.py:437–445`.

**Attack vector / reproduction:**

1. Resolve either checked-in stage/prod parameter profile. Neither overrides `enableGuardrails`, whose root default is `false`.
2. Follow the agent pattern: shared sessions and guardrails are disabled, while the root enables external ingress, model-selected movie tools, and the Azure model configuration.
3. Call `configured_safety` with the live settings and both enable flags set to `false`: it returns `(None, None)` without rejecting the configuration.
4. In a deployment with the remaining credentials and roles configured, model requests use process-local accounting. A process replacement clears that accounting, and operator global-stop policy is not consulted.

**Observed evidence:** Local configuration probe printed `azure (None, None)`. This is a confirmed deployment/configuration path, not a claim that stage/prod is currently deployed or reachable.

**Root cause / impact:** A development fallback remains valid for the live hosted path, and the production profiles inherit it. Authentication and local per-run limits still apply, but durable daily limits, shared containment, protected shared-control audit, and cross-restart accounting do not. A caller can receive a fresh daily budget after each operational restart/redeployment. A published shared stop policy has no effect on such a runtime.

**Concrete remediation:** Make shared controls mandatory at the hosted live-model boundary. For example, in `from_env`, reject live settings unless both `ENABLE_GUARDRAILS` and `ENABLE_SHARED_SESSIONS` are `true`; retain fake/offline teaching mode as an explicit separate path. Explicitly enable controls in stage/prod profiles and provide their environment-specific storage, policy bootstrap, cleanup, identities, and roles before promotion. Add an infrastructure contract that fails stage/prod validation if live models or external ingress are combined with disabled controls. Do not simply turn flags on without provisioning their dependencies.

Suggested runtime invariant:

```python
if settings.mode == "azure" and any(
    os.environ.get(flag, "false").lower() != "true"
    for flag in ("ENABLE_GUARDRAILS", "ENABLE_SHARED_SESSIONS")
):
    raise ValueError("Hosted live models require shared controls and sessions")
```

**Regression requirement:** Hosted live startup without either control fails; approved profiles preserve accounting after service recreation and deny admission under a stopped policy.

## SR-03 — Medium: One user can occupy every shared session slot

**Location:** `apps/agent/src/az_maf_agent/guardrails.py:168–184`.

**Prerequisite:** Any admitted API user on the shared-session deployment.

**Attack vector / reproduction:**

1. As A, call `POST /sessions` 1,000 times. No chat, model, or tool operation is necessary.
2. As B, call `POST /sessions`.
3. Observe `429 {"error":"session_capacity"}`.

**Observed evidence:** A obtained 1,000 sessions; B was denied. The daily model accounting remained empty.

**Root cause / impact:** Session admission checks only a global count. It has no per-owner limit or creation-rate budget. Registrations expire at the configured maximum lifetime (four hours), even though idle sessions become inaccessible after 30 minutes. Reset does not release a registration, and there is no session-close route. A single admitted user can prevent everyone else from starting sessions for up to four hours; existing sessions can continue.

**Concrete remediation:** In the same atomic registration transaction, enforce a configured per-owner active-session cap and a per-owner session-creation rate limit. Keep the global cap as a final safeguard. Add an owner-authorized close operation that fences in-flight work and releases registration safely; reconcile expired idle sessions with admission records. Never implement the per-owner check outside the transaction.

Example transition logic after expiry pruning:

```python
owner = scope_ref(principal)
owned_count = sum(s["owner"] == owner for s in state["sessions"].values())
if owned_count >= configured_per_user_session_limit:
    raise Denied("user_session_capacity")
```

**Regression requirement:** Reaching A's cap still permits B to create a session; concurrent admissions on separate replicas cannot exceed A's cap.
